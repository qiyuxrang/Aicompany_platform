## 目标结构

React统一业务与管理入口 → Django平台身份/授权/适配 → 各独立业务能力。

- 产品：Django任务与人工批准 → 持久任务交接 → 独立worker与LangGraph → 模型/RAGFlow/原文档工具。
- 人事：平台可信身份 → 保留的招聘与转正FastAPI业务服务；AI后台执行与确定性审批分开。
- 经营：平台授权查询 → 原经营Django及其数据库；不在平台重算财务。
- 工程：E0先落实数据与交接；E1仅在批准专业范围内提供辅助。

首期允许同机分进程，文档worker不占用网页请求。不得以此默认引入第二套完整微服务平台；也不得用临时后台线程冒充可恢复任务系统。

## 文档执行状态

业务状态与执行阶段分开。业务状态建议为DRAFT、WAITING_INPUT、QUEUED、RUNNING、WAITING_REVIEW、FAILED、CANCELLED、COMPLETED；阶段为INTAKE、BLUEPRINT、WRITING、CONTENT_CHECK、RENDER、FINAL_REVIEW。命名可在获批设计中统一，但语义不能遗漏。

正常路径：DRAFT → QUEUED → RUNNING/INTAKE → RUNNING/BLUEPRINT → WAITING_REVIEW/BLUEPRINT → QUEUED → RUNNING/WRITING → CONTENT_CHECK → RENDER → WAITING_REVIEW/FINAL_REVIEW → COMPLETED。

缺项进入WAITING_INPUT，补充产生新输入版本；退回进入相应修改阶段并保留历史；技术失败进入FAILED，获准重试创建新attempt；取消在执行者停止或失去有效写入租约后进入CANCELLED。在途取消前显示请求已提交，不伪称停止。COMPLETED仅指当前范围人工批准，扩展或改稿另建版本。

## 状态权威与可靠交接

- Django保存业务任务、真实批准和成果版本，是产品业务状态权威。
- LangGraph检查点只描述执行进度；任务ID由服务端关联，不能凭客户端thread_id跨任务恢复。
- 原工具回执用于核对输入输出字节与复用条件，不能替代批准。
- 人事和经营正式业务状态仍由原业务服务维护；门户只展示明确关联的状态。
- 批准事务与恢复请求必须可靠衔接：持久化待执行动作或使用现有事务投递机制，失败可重试且不重复恢复；禁止“已批准但只发了易丢内存通知”。
- worker需持久领取、租约/所有权、心跳或可验证停止、attempt/fencing标识、有限重试和迟到结果拒绝。具体复用何种队列由T-G02评估一次确定，不自行开发通用调度平台。
- 文件先写新版本临时位置，校验成功后登记成果；重复运行不能覆盖批准文件。业务库与文件失败时保留可对账状态并提供清理规则。

## 拟定文档接口

以下为设计合同，不宣称现有API存在。路径可在技术评审时调整，语义和权限测试必须保留。

| 操作 | 拟定接口 | 最小合同 |
| --- | --- | --- |
| 建任务 | POST /api/product/tasks/ | 输入引用、文档类型、用户要求、Idempotency-Key；用户由会话决定 |
| 查任务 | GET /api/product/tasks/{id}/ | 状态、阶段、版本、可执行动作、脱敏错误，不返回任意路径 |
| 改蓝图 | PATCH /api/product/tasks/{id}/blueprint/ | expected_version与修改内容；陈旧版本409 |
| 作决定 | POST /api/product/tasks/{id}/decisions/ | artifact_id、version、hash、approve/revise及意见；操作者来自后端 |
| 取消/重试 | POST /api/product/tasks/{id}/cancel/ 或 retry/ | 当前版本与原因；按允许状态转换并幂等 |
| 下载成果 | GET /api/product/artifacts/{id}/download/ | 重新检查对象权限；区分草稿/批准版本 |

通用错误：401未认证，403无权限，404未找到或按策略隐藏受限对象，409版本/幂等冲突，413超限，422输入校验失败，429限流，503依赖不可用。返回稳定错误码、用户说明和request_id；不回显秘密、绝对路径或原始敏感正文。

用户来源、管理员权限和批准人不得从客户端字段直接采信。业务前端不能直接调用模型或持有机器密钥。跨系统接口必须由D-08固定信任目标、字段白名单、身份绑定、过期/重放防护及撤权规则。

## 模型工具与质量保护

独立模型只执行获准资料范围内的任务；Skills中的知识和写作要求按阶段加载，强制审批和权限落到代码。工具使用允许列表、任务根约束和资源限额。RAGFlow检索携带授权范围，来源失败、无命中与冲突分别记录。

产品质量先冻结content.json等实际内容合同和模板资产，不同时更换模板、生成器与Office。先对固定输入完成格式回归，再替换模型执行；同模型不同上下文也不能直接视为质量等价。长文并行章节使用同一事实版本，最终检查跨章一致性。

招聘结果与缓存绑定授权、原文、标准、规则和模型版本，程序负责加权。UNKNOWN不得自动按FAIL处理。转正AI只辅助，不成为状态机的批准者。经营和工程金额不交给模型作为权威计算。

## 部署与运维

先采用隔离数据库和脱敏样例。PostgreSQL可保存平台任务与执行检查点，但表/命名空间、迁移和清理归属分开；不借此合并原人事/经营库。文件目录按任务隔离并受服务端控制。

Office COM运行环境需单独验证服务身份、安装、并发与故障清理；不能宣称原Windows渲染在Linux容器自动兼容。必要时分离渲染worker，但不改渲染器来悄悄降低格式标准。

正式部署前确认TLS、网络、密钥、备份恢复和保留期。回退优先关闭新增入口/执行器并保留旧系统；有迁移时先验证向前/回退兼容，禁止直接恢复覆盖正式数据。平台故障不应迫使原经营台账停用。
