## 1. 产品目标

- 企业多部门 AI 业务协同平台。
- 以业务任务为中心。
- 不做通用 WorkBuddy。
- 普通员工不直接操作模型、Skill、编排图。

员工通过业务工作台提交资料、处理问题、审核与下载成果；平台统一身份与治理，各业务保留自己的规则与数据。

## 2. 总体架构

```
React ──▶ Django / DRF ──▶ 业务模块 ──▶ 模型网关 / RAGFlow / 后台 Worker / 原业务系统
```

- **React**：统一业务与管理入口，保留既有页面风格，不新增第二套前端。
- **Django / DRF**：服务端身份、对象与动作权限、任务与人工批准、审计、业务状态权威。Django Admin 负责平台管理。
- **业务模块**：产品方案、人事协同、项目经营、工程成本、Tender。
- **模型网关 / 后台 Worker**：产品后台 Worker 调用现有 FastAPI 模型网关、受控检索适配器与原文档工具；模型不能自行批准。
- **RAGFlow**：只提供授权检索。
- **原业务系统**：人事、经营等的原始服务与数据库保持原位，作为该领域数据权威。

所有列出的能力均**复用现有实现，不重复建设**：不另建门户、权限、审批、审计、任务系统，不另建第二套检索或第二套前端。不为架构标签（如 LangGraph）重写现有可靠执行链。

## 3. 核心规则

- **服务端身份和对象权限**：以服务端身份与授权结果为准；浏览器自报的 user_id、角色、部门只视为普通输入。模块入口权限不等于查看全部资料，任务、蓝图、简历、评价、经营明细、附件、导出、批准都按用户与对象授权。管理员默认只管平台；总经理默认只获明确授权的经营范围，不自动获得人事正文。原业务端只接受经验证的服务端身份上下文，不信任浏览器自报身份。
- **人工批准绑定具体版本**：批准必须由获授权用户针对当前精确版本（版本 + 哈希）执行，并保存实际操作者；旧版本批准返回冲突，关键路线变化须形成新版本并重新批准。
- **AI 不得自行批准**：模型不能调用接口替人批准；模型口头"已同意"、伪造 approved 字段均不能触发正式成果生产。
- **UNKNOWN 不等于 PASS**：未知、未查、未取得、未检索到，均不得记为通过；同时 UNKNOWN 也不得自动等同 FAIL。
- **未验证不得写通过**：无真实证据、未执行或阻塞的步骤，不得标记为通过；不得以降低门槛、删除条件或降低严重级别掩盖失败。
- **一个阻塞只阻塞依赖它的任务**：未确认条件只阻塞依赖它的任务，其他已获批且无依赖的工作可继续。
- **真实数据、模型、外部来源、部署按授权边界执行**：真实资料外发、真实模型调用、外部来源接入、正式部署分别需要授权；未获授权的一律在调用前阻断并显示真实原因。隔离实现与文档整理不受阻断。
- **本地 checkpoint 与 Git 边界**：允许在获批 branch/worktree 内按 Feature Batch 创建本地 checkpoint；禁止自动 push、merge main、reset、clean、stash 和覆盖未知成果。

- **核心边界**：不另建 AI 平台，脱离 WorkBuddy 独立运行，复用原规则、模板、内容合同与工具；不新增通用工作流、聊天机器人或自动学习规则。

### 4.2 人事（HR-001～008）

- **目标**：JD 生成、简历分析、转正协同（H1 招聘、H2 转正）。
- **核心边界**：Django 为统一身份与权限入口，优先复用现有招聘 FastAPI 服务，不决定迁库/合库/重写；AI 输出均为辅助信息，最终业务责任由获授权人员承担；不恢复已取消的人才库。
- **关键验收原则**：改浏览器 user_id 不改变权限；JD 必经"录入→缺项→生成→HR 修改→HR 确认"闭环；简历评分须先经 HR 确认标准并完成 D-04；每项判断须可定位到原文证据；总分由程序按已确认规则加权计算，模型不得直接给出不可复算的最终分；评分不自动产生录用或淘汰结论；转正使用确定性状态机，AI 不可用时人工流程仍可走完。

### 4.3 经营（BIZ-001～006）

- **目标**：统一入口与授权经营看板（总览、销售、工程进度、财务、项目详情）。
- **核心边界**：**原业务数据为权威**；不合库、不重做金额规则、不增加 AI 算账或通用 BI 设计器，不保存第二套可编辑财务账；总经理默认只读；本期不默认实现 SSO。
- **关键验收原则**：经营权限不自动开放人事正文；同一用户、期间、筛选下平台与旧系统项目集合与指标一致；汇总不因翻页改变；正式金额与原系统同口径对照，不在前端或模型重算；离线、超时、空结果与真实零值四种状态可区分，未取到值不得显示零；撤权后旧链接不可继续取数。

### 4.4 工程（ENG-001～005）

- **目标**：清单、定额候选、人工审定、计价交接（E0 盘点、E1 试点）。
- **核心边界**：只明确一个主营专业与适用依据；定额计价、内部预计成本、商务报价三类分开；模型建议不等于审定套项；不假设专业工具具备可用接口。
- **关键验收原则**：D-05 依据不齐则阻止正式套项计价，不生成看似正式的定额编号或金额；清单保留原行号、规格、单位、数量与来源，缺项明确列出；金额由确定性程序或获批专业工具计算，以审定工具输出为准，不因总价接近就通过；已批准成果只读，导出标明类别与审批状态。

## 5. 产品 P1 主流程

```
资料上传
  → 事实 / 冲突 / 缺项解析
  → RAGFlow 授权检索
  → 蓝图
  → 人工批准
  → 分章生成
  → 检查
  → 人工确认
  → 正式成果
  → 版本归档
```

流程约束：

- 事实、推断、冲突、缺项分存；推断注明依据且待确认，冲突并列各来源，禁止模型自行覆盖事实。
- 只检索获授权资料，不传递无关部门或人事内容；检索的授权校验在调用前后与阅读/发布时复验。
- 蓝图批准绑定完整版本，未获授权人员批准不得生成正式正文。
- 检查结果至少区分通过、失败、未知、未检查、待人工；不生成虚假综合质量分。
- 自动通过仅为待审核稿，正式成果须获授权人批准；版本归档不可覆盖旧版，日志不可被正常角色改删。

**P1 的三类正式成果**（可研与 PPT 于 2026-09-23 由 P2 归入 P1，编号不变）：

- **技术方案 Word**：主流程交付物，复用已冻结母版与 Office 链路，经目标环境真实渲染。
- **可研性报告（PRD-009）**：与技术方案共享输入事实与版本，但独立回答必要性、备选方案、实施条件、风险与经济资料边界；**不能复制正文换标题**，缺少成本或收益依据不得编造经济结论。
- **PPT（PRD-010）**：从已审结构化内容 ID 派生，保留来源与版本，优先复用现有 PPT 工具，**不反复解析 Word 猜内容**；源内容变化时标记影响范围与过期状态。

三类成果**独立生成、独立渲染、独立验收、独立版本管理**，互不替代（Word 生成通过不代表 PPT 质量通过）。

## 7. 开发与验收方式

每个 Feature Batch 按固定顺序推进：

```
范围确认 → 实现 → 测试 → AT → Evidence → 本地 checkpoint → 下一批
```

- 先确认本批任务 ID、可修改文件与适用决策项；范围不清时只做只读差距核对。
- 先写失败用例，再最小实现与验证；普通实现自主推进，外发资料、修改旧项目、新增依赖、变更业务规则与部署另行确认。
- 每项 AT 登记规范/代码/环境版本、授权输入、预期与实际、命令或浏览器步骤、证据位置与结论；可用结论为未执行、通过、失败、阻塞、不适用。
- 证据独立存放并保留失败记录；新结果追加至执行状态文件，不改写旧包历史结果。

**验收层次必须区分，不得互相顶替**：

| 层次 | 说明 |
| --- | --- |
| 技术测试 | 单元/契约测试，只证明代码行为 |
| 真实依赖验证 | 真实模型、真实检索、真实外部来源（需对应授权） |
| 浏览器验收 | 端上真实交互与渲染可用 |
| 业务签认 | 产品、HR、经营、运维负责人签认，实施方不可代签 |
| 部署验收 | 目标环境、备份恢复、回退条件满足 |

测试替身、模拟调用、预置内容或文档结构检查，均不能混为真实通过；截图不能单独证明后端授权。未执行写未执行，不给虚构的总完成百分比。

### 前端延期规则（Frontend Deferred Rule）

当前阶段允许优先完成产品 P1 的**后端、Worker、数据、权限、版本、三类成果生成与自动化验收**。
前端业务逻辑与交互优化可延期至 **Core Backend Closure** 之后统一实施。

- 若某 Task 的后端 / 核心能力已通过、但前端尚未接入，**记录为 `CORE_PASS / FRONTEND_DEFERRED`**。
- **不得**据此将该 Task 的 Browser E2E、或整个 P1 标记为 `PASS`。
- 前端延期**不得阻止**与其无直接依赖的后端 Task 继续执行（与「一个阻塞只阻塞依赖它的任务」一致）。
- 前端延期是**范围限定**，既不是失败，也不是整体通过；不得用于掩盖未接入状态。

**P1 最终完成前必须补齐**：

- 前端业务流程
- 浏览器真实 E2E
- 三类成果（技术方案 Word / 可研性报告 / PPT）的真实下载与审核流程
- 适用业务签认

上述四项补齐前，P1 **不得进入发布验收**（与第 6 节 P1 发布验收门槛一致）。

- 自动投标。
- AI 自行正式计价。
