## 4. 固定接口契约

### 调用链

浏览器带**平台会话**请求 `GET /api/business/summary/` → 门户重查自身权限与映射并发一次票据 → 门户服务端POST旧桥接 → 旧服务端向门户POST兑换 → 用兑换所得旧User主键执行旧权限及只读查询 → 门户校验响应和当前授权再返回。

旧端不得调用 `login()`、创建浏览器Session或使用共享管理员，不读取/共享门户Session数据库。该链条不是浏览器SSO。浏览器不能自行提交或选择旧用户ID、角色、部门、回调地址或查询目标。

### 旧端新入口

- 方法/路径：`POST /api/portal-bridge/summary/`。采用POST只是把短效票据放在请求体中，**不代表允许业务写操作**；GET及其他方法拒绝，关闭时404。
- 认证：`Authorization: Bearer <独立服务秘密>`，仅服务端，常量时间比较；不接受原生旧Session作为桥接认证，也不修改其他接口的原生认证。
- JSON仅接受 `ticket`、`audience: "business"`、`purpose: "read_summary"`；错误类型、超长输入及多余的身份/目标字段拒绝。
- 固定回调 `POST /api/integration/redeem/` 使用相同机器认证及同样三字段；兑换响应只取 `external_user_id`、audience、purpose，校验类型/用途，再按旧系统整数User主键查找。映射建立时保存旧User.pk的十进制字符串，不按姓名或显示名模糊匹配。
- 门户映射唯一，未映射/映射停用在门户拒绝；旧主键不存在、旧账号停用、旧账号要求首次改密均拒绝，不自动创建或修复旧账号。
- 开关拟为 `LEDGER_PORTAL_BRIDGE_ENABLED`（默认false），固定回调配置 `LEDGER_PORTAL_REDEEM_URL`，服务秘密 `LEDGER_PORTAL_BRIDGE_SECRET`（默认空，启用时至少40字符）。秘密通过受控环境注入，不写入源码或实际旧.env。
- 正式配置只准HTTPS；隔离验收允许显式DEBUG下的回环HTTP地址。目标固定且校验，不跟随重定向，不使用任意代理环境；兑换超时短于门户当前3秒上游等待（拟2秒），请求与响应体有限制。不得通过关闭安全校验解决配置错误。

### 只读响应（沿用门户现有结构）

```json
{
  "projects": [{"id": 101, "name": "隔离测试项目A"}],
  "summary": {"project_count": 1},
  "source": "legacy-ledger:authorized-projects",
  "updated_at": "<带时区ISO时间>"
}
```

上例仅是**接口结构示意，不是已执行结果**。本轮不返回财务金额、项目编号、身份详情、电话、客户、备注、部门列表或其他业务字段；不使用完整ProjectSerializer。`project_count`是旧端当前授权集合的真实数量，不由门户估算。`updated_at`明确表示这次查询快照的生成时间，不冒充业务记录最后修改时间。

项目按确定顺序返回；空授权集合为200及空列表/数量0，与错误分开。维持门户最大1000个项目、256KiB返回体的现有限制，超限显式失败，不静默截断并声称全部项目。若需要分页另行确定，不在这轮凭空增加分页平台。

### 失败契约

| 情况 | 旧端/平台预期 |
|---|---|
| 旧桥接未启用 | 旧端404；平台报告未接入/不可用，不冒充成功 |
| 请求体无效、非法用途/目标、试图提交user_id | 旧端400或403，绝不使用提交身份 |
| 服务秘密错误、票据错误/过期/重放、映射用户不可用 | 403，平台对应权限失败 |
| 未授权任何项目 | 200，真实空列表和0，不是403的替代 |
| 回调/上游离线、超时、3xx、无效JSON、响应过大 | 失败关闭；门户503且不展示旧缓存或Mock数据 |
| 不支持的方法 | 405（桥接开关开启时） |

每次业务读取都使用新票据；失败后的重试不复用已消费票据。秘密、票据、Cookie和Authorization不进入URL、浏览器、审计或请求日志。

## 5. 权限复用方式与撤权

现有实际源码：

- `backend/ledger/models.py` 的 User已保存role、department、is_active、must_change_password；不需要新增profile表或新账号模型。
- `backend/ledger/permissions.py:7` 的 `BusinessAccessPermission.has_permission()`负责旧账号认证/首次改密限制，当前还包含资源级读取限制。
- `backend/ledger/views.py:75` 的 `accessible_project_ids(user)`是原项目行范围逻辑：manager可见全量，department用户按已有Project.departments过滤。
- `backend/ledger/views.py` 的 `LedgerViewSet.get_queryset()`使用同一函数进行原生项目过滤。因此新桥接只复用该函数筛选 `Project.objects.filter(pk__in=...).values("id", "name")`，不另写一套部门规则，也不直接透传全字段原生列表。

新入口使用自己的机器认证适配，兑换后将**真实旧User**交给现有 `BusinessAccessPermission`；显式补足旧User存在且is_active检查，不只依赖is_authenticated。因为POST承载的是只读票据，不能把“POST被允许”视为财务/其他资源读取许可；唯一查询资源限定为原生projects读范围，仍须逐项目范围筛选。不会借桥接读取dashboard、contracts或receipts。

每次请求重新读取旧User和项目范围，不缓存角色/部门或授权结果。旧User停用、角色/部门变更、Project.departments变化后，下一次桥接与旧原生查询必须一致；不宣称能收回已返回的数据。在途请求以最后服务端权限检查为边界。

平台侧撤权/停用阻断下一次平台请求、兑换及摘要返回前校验；撤权恢复不复活既有票据。**旧原生登录、旧Session及直接旧网址不随平台撤权自动停用**，验证时必须证明它们仍按旧权限工作。本轮不改这条边界。
