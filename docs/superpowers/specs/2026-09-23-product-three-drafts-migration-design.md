# 产品事业部三种草稿接入现有平台设计

日期：2026-09-23。状态：待用户审阅；本文件是迁移设计，不是备份完成、正式成果发布或真实资料外发许可。

## 目标与验收边界

现有产品事业部任务支持同一项目输入生成技术方案 DOCX、可行性研究 DOCX，以及基于两份报告内容的 PPTX，三者均只作为**待人工审核草稿**供有权人员查看和下载。先以合成资料制作两份约 1000 字的 Word 样稿和一份与内容相称的 PPT 样稿，检验三类文件格式、同源关联和失败保护；1000 字不是产品的字数上限，也不为满足旧项目长篇幅或页数要求凑字凑页。

用户确认 `C:\Git_projects\bj_device_company` 中的 Word 模板已审核：不得修改该源仓库的 Word 模板，也不得覆盖平台已冻结的技术方案 Word 模板。此确认只说明模板选择，不替代当前业务资料、模型费用、人工成果质量和正式发布的批准。PPT 没有固定模板，参考旧项目的双报告交接、汇报大纲、逐页来源绑定、生成与逐页检查模式；`模板文件/` 的客户 PPTX 不直接迁入平台。

## 已有基础与需补缺口

- 平台已具备 React 产品工作区、Django 身份/对象权限/任务/版本/审计、FastAPI 模型网关、技术方案 DOCX 冻结资产和草稿渲染。已冻结技术方案 `template.docx`、`profile.json`、`prototypes.xml` 与源仓库同名文件逐字节一致，继续复用，禁止改写。
- 源仓库 `skills/bj-docs` 提供可研模板及内容合同、双报告输入/交接工具；`skills/bj-show` 提供 PPT 工作模式。部分脚本依赖 WorkBuddy 宿主或外部 PPT Master；平台不得运行时依赖源工作树或把整套 WorkBuddy 环境搬入。
- 当前平台 `DocumentTask`、`DocumentRevision`、`DocumentArtifact` 与 worker 面向技术方案单一流程，不能把三类成果混用同一审批状态、文件版本或错误码；需在既有任务边界内扩展用途/关联，避免新建第二套门户、审计和审批系统。
- 现有 P1 默认关闭模型调用、费用策略、授权检索、Office 正式渲染和发布。先前单次模型直连只能证明厂商接口可用，不能证明平台网关与业务生成已打通。

## 备份先行与只读来源

实施前记录平台和源仓库的 HEAD、修改/未跟踪文件清单及哈希，不重置或隐藏用户成果。使用新建、受限且 Git 忽略的备份目录，保存本轮将改动的工作区文件、对应差异及必要的当前平台私有工件；仅备份数据库不足以保护草稿文件。先确认 P1 隔离数据库身份和存储根目录，再做一致快照，恢复到**新的**数据库和**新的**私有目录，以记录、文件 SHA-256 和受权只读下载核对可恢复；任何目标已存在即停止，不覆盖原库、已有测试库或日常环境。备份/恢复失败时不启动迁移。保留原备份，不自动删除或覆盖。

源仓库始终只读，按具体文件登记来源路径、源码版本/工作区状态、哈希、依赖和授权；只迁入可研模板的必要文件与验证后的最小工具闭包。既有技术方案冻结资产原字节不变；可研资产放在平台新增目录，运行时执行哈希校验。绝不以客户 PPTX 或旧项目中的专有联系人、资质附件作为通用内容源。

## 生成与版本数据流

同一平台产品任务保留一份输入事实与来源版本；生成两个独立报告内容版本，分别标识 `technical-solution` 和 `feasibility`。蓝图/输入批准遵守既有对象授权与精确哈希约束；可研按必要性、备选路线、实施条件、风险和经济性证据边界展开，不复制技术方案换标题。每份报告的模板版本、规则版本、输入哈希、章节/内容 ID 和文件哈希可追溯；未核实资料及缺项保留为待确认。由现有 worker 的租约/fence/次数限制持久执行，不由浏览器后台常驻执行。

两份报告内容完成后构建可核验的同源交接记录：逐个选取已保存内容块，使用 `family:block_id` 区分两个报告中重复的 ID，携带来源、需求及全部 pending，绑定报告版本及哈希；交接记录不自动继承人工批准。PPT 大纲和逐页引用只消费该精确交接版本，标题、数字和结论不得靠重新解析 DOCX 补造。任一输入、报告内容或所引用资料变化使相关 PPT 草稿过期；查看历史版本时明确标记过期，作为当前有效草稿下载时由服务端拒绝，历史文件留存且不覆盖，不以页面显示为唯一保障。

PPT 首批不固化某一客户 PPTX 或企业主题。先按源项目工作模式验证可在平台独立、稳定运行的最小 PPT 生成路径：必须有可编辑 PPTX、逐页来源 ID、正确版本绑定和可重现的渲染输出；原模式的 PPT Master 若要求 WorkBuddy 模型、外部下载安装、不可用的授权/预览门禁，则明确报告阻断，不以未审查的替代引擎悄悄宣称等价。生成方式与依赖在实施计划中根据只读工具验证冻结，不新增并行万能 PPT 框架。

所有文件放平台私有存储，经现有产品任务对象权限访问；保存到新路径并计算哈希后才登记，不覆盖已生成版本。AI 只写草稿，不执行审批；下载标识待审核，产品正式发布开关保持关闭。后续正式业务签认另行实施。

## 错误处理与边界

缺输入、来源冲突、模型不可用、格式工具不兼容、模板哈希不符、Office/PPT 渲染失败或内容超出容量时，记录可辨错误与待人工处理状态；保留已完成版本，失败任务不冒充成功、不自动扩大外发范围。撤权、陈旧版本和迟到 worker 写入仍按现有后端检查拒绝。上传文件、外部资料和模型输出视为不可信输入，不能作为系统指令或审批。

合成资料隔离样稿可用明确获准的模型配置，但默认不调用外部服务。真实模型调用必须在隔离环境完成用途路由、精确外发范围和真实费用上限的配置核对；未具备时可用人工内容验证模板/结构路径，并将真实模型链路记为阻塞而非通过。不得使用聊天中暴露过的 Key；密钥仅由受限环境配置提供，日志不记录正文与密钥。RAGFlow 原生适配和公司真实资料不因本设计获授权。

## 分批实施与验收

1. **保护与差距核对**：备份、非覆盖恢复、原文件哈希和代码/依赖适配清单均通过才继续；变更只落平台，源仓库 before/after 哈希相同。
2. **双报告草稿**：优先复用技术方案原链路，接入可研模板及有据写作规则；合成输入产出约 1000 字的两份独立 DOCX，核查模板/文件哈希、可编辑、来源、缺项、权限和实际 Word 渲染，版本变化不复活旧批准。
3. **同源 PPT 草稿**：仅消费双报告的明确内容版本及来源块；生成 PPTX 并逐页检查内容、可编辑性、溢出、乱码和来源绑定；修改任一报告后的过期标记、当前有效草稿下载拒绝和重生成用例通过。PPT 页数服从实际内容，不套旧 22 页下限。
4. **整体回归**：隔离 PostgreSQL 中执行迁移、后端全套及并发/越权负向测试；前端类型检查、测试和构建；浏览器走现有产品入口验证三种草稿及错误状态。既存 `test_portal_phase1` 不可覆盖，测试用新隔离库；数据库和私有工件一并做恢复对照。每类技术验证、真实模型调用、业务质量、目标环境渲染和正式签认分别记录结论，不互相替代。

验收结果只称“隔离环境三种待人工审核草稿可生成”，前提是三种文件均由平台实际运行并可验证；若 PPT 工具链受宿主限制，则仅已通过的批次成立，整体不得标通过。正式资料、正式模板发布、生产部署、PPT 商业主题选择及其他部门功能均不在本迁移批次。
