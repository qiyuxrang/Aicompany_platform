## 1. 目的与成功条件

产品人员在现有 `/centers/product` 的侧栏点击「商机获取」，立即查看实际入库的公开招标/采购公告；点击「刷新」可请求后台按四来源顺序补采新公告，页面显示排队/执行/结果并更新列表，**不在 HTTP 请求中等待爬取**。列表可按来源、地区、采购单位、类型和时间等既有字段筛选，详情展示有依据的标题、采购单位、预算、地区、发布时间、截止时间、来源、变化版本和**该公告实际核验的官方详情页链接**。没有可信字段则显示「未知」，不得猜 ID/地域、生成示例公告冒充采集结果。页面能打开但无真实公告，仅证明页面接入，不证明用户的最终目标已经满足。

分三个独立门槛：**A** 在目标仓库的隔离分支及全新隔离 PostgreSQL 验迁移、现有产品登录访问、页面/刷新入队→独立后台消费者→状态及合成数据更新的离线闭环，真实采集默认关闭且零外站出站；**B** 另行明确批准后，按固定三日窗口受控逐源真实首次采集，并在产品账号页面看到至少一条可核对的真实公告与对应官方原文、验证点击刷新能后台补采可信新增，或如实记录窗口内没有可入库公告而保持 `NOT_VERIFIED`；**C** 目标环境部署、专用队列消费者及出站配置另行审批。A 不能冒充 B/C；B 有公告也不能自动批准 C。若来源窗口内确无合格公告，不为凑数扩大窗口或使用独立库的旧数据。

## 3. 数据与接入架构

从目标仓库 `main` 建**仓库外隔离工作树和功能分支**；它当前已有用户未提交的 Product/设置变更，绝不 stash/reset/checkout/覆盖这些文件或向日常库执行迁移。从目标仓库既有 Django/DRF、`portal.User` 和产品模块登录访问机制、审计、CSRF、私有存储与 React 产品工作台适配 Tender 专有表/API；不复制独立工程 `tender` app 的 0001–0009 迁移或另一仓库 `portal.0012–0013`，应从目标仓库当前 `portal` 迁移末端生成迁移并在新隔离 PG 验索引与数据约束。Tender 公告、快照、来源健康与租约为独立领域对象；不插入/改写产品 `DocumentTask`，不跨来源按项目编号合并商机。

选择性复用已经冻结的安全出站、四个适配器、来源内幂等、原始快照、版本/事件、批次唯一槽、失效即停及人工恢复审计；适配器的读取必须经过既有 `TenderOutbound`，保持 TLS 验证、固定来源白名单、低频和重定向边界。商机浏览、刷新入队和状态读取仅复用目标平台**现有**产品事业部登录访问校验：能进入产品工作台的登录且激活的产品用户即可操作，不新增 Tender 角色、额外操作员名单或业务权限配置页；未登录、非产品用户、必须改密码及停用账号仍由后端拦截，管理员预览不调用业务 API。若以后接入企业资质原件，必须另行设计敏感文件权限，不能借普通商机阅读授权。采集及手动刷新两个**后端环境开关**在 A 阶段默认关闭，B/C 的实际出站启用另行批准；开关关闭时点击刷新须明确返回「采集未启用」，不能入队形成永久等待。`--force`、`--preflight` 和直接 Worker 调用不得绕过关闭门槛；过期来源/批次不能自动接管，运维人员核实旧执行节点退出后才可通过受控管理命令显式恢复且留持久审计，此为故障处理而非日常用户权限。

数据链：来源的真实列表引用 → 核验发布时间及站点/公告详情映射 → 抓取并校验对应详情 → 私有原文快照及哈希 → 结构化字段/来源内公告 ID 与版本 → 授权 API → 产品事业部商机列表/详情。API 给出真实官方 HTTPS 原始详情 URL；后端只持久化适配器允许的官方域名与详情路径，前端以普通 `<a target="_blank" rel="noopener noreferrer">` 打开，不对任意第三方 URL 做后端跳转，也不把附件 URL 当官方详情页。链接只证明**采集时匹配并验证**；外站之后可能下架或改内容，页面需同时给出当时的已采集时间与版本/快照信息，不保证用户每次点击外站仍可访问。外站文本作为不可信内容展示，不在页面运行原站脚本/原始 HTML。

### 点击刷新与后台执行链

页面进入时只读数据库，不因打开页面自动采集。点击「刷新」发带 CSRF 的 POST，后端校验现有产品用户身份、两采集开关及四来源名单，在单活跃批次约束下原子入队；返回批次 ID 和 `QUEUED`（已有待处理/执行批次时返回 `409` 及**原批次 ID**，页面接续该批次而非重复创建）。刷新按钮仅在可用时启用；首次三日补录及可信增量边界未另获批准前不开放页面刷新入队，未启用、消费者不在线、来源受阻或批次中断均要明确可读的提示，不能把排队伪装成已采集。页面短时轮询该批次状态（`QUEUED/RUNNING/SUCCESS/PARTIAL/FAILED/INTERRUPTED`）并可离开/重进后恢复查看；结束后重读列表及各来源状态，展示新增数、失败原因码与最近成功时间。轮询仅查本地数据库，不自动重新入队；请求失败和过期中断须停止无限“刷新中”动画。

Tender 专用后台消费者从数据库领取批次、顺序执行四源；**不能仅移植独立版「Web 入队后人工运行一次命令」作为最终交互**。A 仅用隔离 PG + 离线 fake adapter 验证独立消费者进程确实领取并更新页面，无公网请求；B 获准时受控短时运行并验证真实新增；C 若正式启用按钮，须部署/监控此消费者，使服务在线且开关开启时不依赖人工命令才能消费队列。优先复用已有 Django 管理命令的循环与数据库队列模式，不新引消息中间件、不用浏览器直接爬、不复用 Product `DocumentTask` 的自动过期抢占语义。消费者重启后可认领未开始的 `QUEUED`，但已有 `RUNNING` 即使租约过期也不得自动接管；确认旧进程停止后人工恢复并审计。独立消费者在空闲时定期写入数据库心跳，刷新 POST 先检查并返回已有活跃批次的 `409` + 原批次 ID；新批次入队前由后端检查最近 15 秒内的消费者存活心跳和两个采集开关，不满足时返回可读的「刷新暂不可用」并且**不入队**。消费者在领取后执行采集期间以低频独立心跳更新存活状态，以免正常长时抓取时误判离线；心跳更新失败则 fail-closed 并终止新采集；心跳即使短暂有效也不能单凭它承诺已开始执行批次。消费者正常退出即时撤销心跳；意外退出时最近心跳至多 15 秒内可能接受一个新批次，该批次若排队超过 15 分钟，批次查询只展示中断/恢复提示而不自动改持久状态；运行途中消费者退出导致批次等待或中断，批次查询返回排队超时/中断状态与恢复提示，不能凭前端计时声称进程离线，也不能无限显示“刷新中”。心跳只用于**用户刷新可用性**，不改变来源/批次的单活跃约束或过期禁止自动接管语义。

## 4. 三日首次采集的严格边界

固定窗口为 `Asia/Shanghai` **[2026-09-26 00:00:00, 2026-09-29 00:00:00)**；起点和终点都是固定时刻，不随实施时间滑动为「最近 72 小时」。以来源发布的**可信发布时间**为准，不使用抓取时刻、公告 ID、标题日期、站点列表排序代替；若来源仅给日期而不给时分秒，按来源明确的当地日期核验，不能从未知时刻制造精确时间。发布日期缺失、含糊或冲突的公告不入此首次窗口，记录原因；正式转换规则须由逐站离线测试和公开样本验证后才可执行。

先只读预检并核对四站各自可扫描的公开栏目、分页、真实日期出处和详情对应关系；对无列表日期的来源，只允许**有界低频**读取可能候选详情来核验发布日，不无界扫历史或制造公告 ID。每站设置有审计记录的页面/候选条数上限；能完整到达窗口下界才可声明该站扫描完整。全国双栏目任何一栏扫描不完整则不推进整个来源边界；首页只有一页的适配器不能据此宣称覆盖了完整三日窗口，若无法到达下界记 `PARTIAL/NOT_VERIFIED`，仅能如实展示已经确认的单条公告，不能说该站三日全量。任何 TLS、登录、验证码、403 或站点保护出现则停该源，不绕过。

首次窗口仅在隔离验收 A 之后**单独授权的运行环境**执行；批次重试、快照与版本采用既有幂等语义：重复抓相同真实详情允许多条时间快照，不重复商机/版本/事件。业务公告即便部分成功，也不能将不完整扫描标为成功或推进边界；失败/中断与上次成功时间对用户和操作员明确区分。窗口前的旧公告不补录；窗口后的刷新按可信首次边界和明确启用时间有界检查**尚未入库或内容确已变更**的公告（重复读取允许，不重复生成商机/版本）。来源若没有可靠完整扫描边界，不得假定旧列表已扫尽而直接跳过未验证区间；仅可报告局部确认的新公告和 `PARTIAL/NOT_VERIFIED`，也不能因用户点击刷新就扩大/移动首次三日窗口。首次三日补录与其后的正常增量是两个显式执行模式：未得到 B 的首次采集批准前，用户刷新不能成为绕开首次数据窗口的隐式入口；正式上线前须另行确认增量启用边界。另验失效恢复与复跑。若实施时已晚于 9 月 28 日，不因此悄悄把窗口改到实施日；无法有界取得并证实三天公告时明确报告差距并请求业务裁决，不无限等待或假称可补齐。

## 5. 页面、异常与授权

产品侧栏增加 `商机获取` section（如 `/centers/product/opportunities`），页面内完成列表、筛选、详情、来源状态及「刷新」按钮/批次进度；保留 `/centers/product` 原项目成果导航、工作台指标与深链，不增加新的顶层中心，也不复用产品项目事实。列表显示公告标题/项目编号、来源、采购单位、地区、预算、公告类型、发布时间、截止时间、状态和更新时间；不为未知数据造数。详情提供「查看原始公告」链接、原文版本/变更、采集时间与来源状态；零数据、扫描中、来源故障、未授权分别显示不同提示，不能把源故障显示为「没有商机」。原生筛选不截断服务端选项；产品用户页面读取公告 API 并在刷新后读取批次状态；管理员预览模式不读取真实商机或批次数据。

目标平台的 `apiRequest` 提供 masked CSRF，不能拷贝独立 Demo 从 cookie 取令牌的实现；后端对 GET/POST 都复用现有产品访问校验，页面隐藏不是鉴权。首次发布默认采集/手动刷新双开关关闭，页面可看已有公告，但点击刷新不得默默入队；B 获准的受控运行仅开放已批准的四来源和窗口并保留执行记录；C 未批准前不在目标环境常驻后台消费者或开启出站。

## 6. 验收、回退与待批准项

- **A（目标接入、真实外站关闭）**：目标仓库新隔离 PG 的空库迁移、索引/约束、系统检查与迁移无漂移；后端/前端全量及产品原业务回归；沿用产品登录校验/撤权/CSRF/原文 URL 约束；关闭采集时点击刷新明确拒绝且零出站，离线 override 时经**独立消费者进程**演练点击→入队→处理→轮询→列表出现合成新增与幂等复跑；来源/批次双进程失效即停；产品浏览器从菜单进入公告与原始链接，管理员预览零业务数据。记录主线现有未提交 Product 改动的隔离方式，不拿另一仓库 21/21 冒充 A 验收。
- **B（受控三天真实样本）**：逐源记录发布日期证据、完整扫描范围、真实 URL 对应正文、入库商机及复跑不重复计数；产品账号在**目标平台**看到已验证公告，点击链接核对原官方详情，并在获准出站的受控环境验证点击刷新确实由后台处理且新公告可见。四源没有合格数据时分别写 `NOT_VERIFIED`，不为完成签收而构造数据；只读与真实采集在审批上分别判断。
- **C（发布/后台消费者）**：独立审查部署的数据库备份、私有存储、消费者启动/在线与故障告警、回退和合法出站；双开关与专用消费者逐项审批。仅当用户按钮可被后台实际消费时才在正式环境启用刷新；不默认新增周期性定时自动采集。撤销产品模块访问/停用账号后 API 立即拒绝，旧原始快照和审计默认保留；不得在共享库做破坏性逆迁移。生产展示、真实采集、后台消费者启用是不同门槛。

**修订规格经审阅后须在实施计划中落实的决议**：先同步 `docs/SPEC.md` 的四源首批变更与旧稿差异记录，再在独立功能工作树按 TDD 选择性移植；未提交的主线 Product 改动不得覆盖。本次刷新交互修订须先经用户复核，再同步既有实施计划供审阅；计划再次获批后才能动业务源码。真实外站抓取及目标部署仍需分别授权。
