### 2.2 不得变更的业务与运行边界

- 单一 Deep Agents Harness + LangGraph Runtime；Runtime 管原生 run、检查点、领取和恢复，Django 管身份、业务事实、根／父关联与最小审计。不得另建通用调度／决策循环或自研替代整套 Runtime。
- 普通问答也绑定 conversation 的技术 root，work／requirement 可空，不强建业务工作；聊天转执行时建立 work／requirement 关联，沿用旧 root 消耗。没有有效 work／requirement，不准业务写入。
- 一个自然语言输入框；简单任务可直接工具执行，复杂任务才按需一层委派；两个获准模型的真实并行与主 Agent 独立工作必须验收。
- 更新可在同一 native thread 创建新 native run；长期 root 工作身份和累计消耗不因此 reset。主 Agent 不忙轮询子状态。
- 产品只由任务 owner 确认精确蓝图版本，随后自动生成技术方案、可研和 PPT；没有 second review 或 final approval 人工门禁。质量检查不是第二审批。
- 正式技术方案不少于 **50000**、可研不少于 **70000** 非空白正文字数；真实正式交付与渲染验收，不用短样例或合成填充替代。
- HR 新策略原件及派生结果长期归档，不按 15 天自动到期；仅迁移仍有效存量，保留授权校验和人工删除，旧失效对象不自动重新开放，已删除资料不恢复。
- 财务员工不能修改其他员工填写的记录；在原业务授权范围编辑本人记录，由可信填写人确认发布本人精确版本。发布集合仅包含本次本人确认版本与先前已发布行，不把其他人的未确认草稿带入。经营看板仅读 pub 版本。
- GM 跨部门只读获准业务原件和成果，不读 private chat／memory、员工 Runtime 文件或检查点，不编辑、不代确认或发布。
- 账号管理仅在人操作入口做批准范围内受限员工操作，不授予 admin／超级用户，不开放完整运维权限；不暴露给 Agent 工具，也不变更网关密钥、模型配置和授权政策。
- 不新增应用费用预算、预留、余额、结算或积分系统；技术终止配置须有限、可证实，不能编造阈值。新增费用与新增外发仍须单独审批。

### 3.1 全批次共用要求

1. 身份来自服务端当前登录／获准服务身份；模型不能传入 writer、账号、部门、权限、namespace、任意下载 URL 或确认人来决定访问权。
2. 将 root 身份、当前要求版本、授权版本、领域对象及其版本／fence 纳入派工绑定；需要补字段时按详细设计最小化落实，不复制业务 payload。
3. 每次读取重新授权；root 可执行校验仅适用于 Agent 发起及其派生的执行动作，业务提交与工具副作用同时核对当前领域 guard。独立人操作与未关联 Agent 的旧任务沿用各自授权及当前领域版本／guard，不以 root 可执行为通用前置；本人发布仍校验填写人、精确修订及发布基线。只丢弃聊天回复不等于阻止 Agent 的旧要求提交。
   执行来源由服务端可信入口／运行关联确定，Agent 工具不能省略 root 冒充独立人操作；人操作触发后续 Agent 执行时，该执行仍须通过根运行准入。
4. 更正／取消与领域提交共用明确事务／锁定顺序；失效通知可重送，但最终提交 guard 必须独立拒绝旧版本。不存在原子跨服务事务时，先使服务端提交资格失效，再异步停止原生 run，并对账。
5. archive 引用实际原件、输入／要求／更正版本、摘要、结果及失败原因；不复制完整敏感资料到审计、不保存凭据或模型私有推理。
6. 恢复、重启、重新领取、同 thread 新 run、并行子分支与自动领域派生共享长期 root 累计终止条件，不能以创建新 run 或新 task 获得新额度。
7. 功能回滚优先停新入口、停新派工和隔离协议，再兼容回退；不自动反向迁移、删除新增归档、恢复已删除资料或覆盖用户未提交修改。
8. 普通问答准入也检查 conversation 技术 root；业务写准入另外要求有效 work／requirement。终止禁用业务动作后，非 LLM 取消、状态核对、在途对账、通知去重与审计收尾仍可执行，但不得再派生业务动作／模型调用或重置额度。

### 3.2 全部规划后统一批量执行

本轮确认的工作方式是：**先将 A0～A5 全范围规划收口，再对整套方案一次审批授权；获批后按依赖连续执行，不每完成一批就重新询问是否继续。** 批量执行不是同时开工所有批次，也不是最后才验证或自动上线。当前仅完善规划，不将“现在进行规划”解释为已批准业务开发。

SSD、详细设计与本计划已分别覆盖业务规则、架构／数据／接口／权限契约、全部任务／验收／失败及回滚出口；不再另建一份重复的“总计划”。批次开始的代码盘点只收敛已规划的真实落点，不留到开发时才决定后续部门的业务规则。

统一执行顺序与处理方式：

1. **规划收口与整稿授权**：核对三稿一致、已确认决定及排除范围；取得明确的整稿执行授权后，登记内容版本／摘要和审批记录，再同步唯一主规范。当前仍未审批、未冻结。
2. **先验证底座，再推进依赖**：A0 验证版本、协议、原生异步、隔离、根累计保护和部署边界；明确最小身份契约后，允许原计划中不依赖未通过出口的 A1 工作并行。未通过 AG-15／AG-16，不使用真实资料，不启动依赖该安全出口的接线。
3. **连续完成全范围**：依原计划推进 A1 身份／历史／项目、A2 产品自主执行、A3 页面／技能／运行闭环、A4 财务／管理、A5 人事／质量。允许的局部并行须有已满足的共同前置和不冲突的修改范围，不把并行当作跳过验收。
4. **边做边验，不逐批重批**：每批完成实现、定向验证及直接相关修复后，记录真实结果并进入可执行的下一批；沿用唯一任务级状态记录。普通兼容适配、最小字段落地和范围内修复可自主完成；进度汇报不等于要求用户重复批准。
5. **失败按依赖收敛**：范围内可解决的技术失败继续修复和复验；无法满足已确认体验或安全出口时，停止受影响执行并说明依赖与可选处理。无依赖的获批任务可以继续，不假报通过，也不以降级成纯聊天、放宽权限或降正式篇幅消除阻断。
6. **统一交付，不自动上线**：最终核对 AG-01～AG-16、真实正式成果、原业务回归、迁移／回滚证据和工程排除边界。生产迁移、部署、Git 提交／推送及新分支操作仍需对应明确授权，不由整稿开发授权自动包含。

仅在以下情况暂停相关动作并询问，不将其扩展为常规逐批审批：

| 需要确认的变化 | 暂停范围 | 可自主继续的边界 |
| --- | --- | --- |
| 新付费服务、明显不同的基础设施成本、替换 Harness／运行路线 | 涉及采购、启用或改变已确认底座的部分 | 已批准环境内、无新增费用与路线变化的验证及独立任务 |
| 扩大业务／数据权限、未获准模型或新增资料外发范围 | 涉及新增访问／外发／业务动作的部分 | 原已批准对象、模型和工具范围内的任务；真实资料仍受安全门禁 |
| 破坏性数据处理、旧失效人事资料恢复、无法核实的存量身份分配 | 涉及该对象或迁移的部分 | 保留原记录与待核实清单，不猜身份、不恢复已删除资料 |
| 生产迁移／部署、长任务维护、提交／推送或创建分支 | 涉及正式环境与版本发布的部分 | 已获准隔离环境实现、测试、证据整理和交付准备 |

以上是范围与授权变化的确认，不是应用内金额预算／审批门禁。整稿授权后，原批准范围内的常规开发、模拟验证和满足既定门禁的获准模型／试点资料测试不逐次重新申请。

### 4.3 A0-02 生产／许可核对清单

- 核实官方 standalone 对 Postgres、Redis、license／环境变量及 beacon 许可出网的要求，记录实际服务／版本组合、支持的生产路径、网络目标和运行责任；以执行时官方资料和获准部署证据为准。
- 官方文档核对结论：standalone 要求 Postgres／Redis、`LANGSMITH_API_KEY`、`LANGGRAPH_CLOUD_LICENSE_KEY` 启动验证及 beacon 许可／usage 出网，airgap 有例外；官方生产测试维护路径为 K8s／Helm，Docker／Compose 示例属于 devtest。这不代表已安装／许可已购／出网已授权或部署已验收；A0 登记实际版本、获准条件和证据引用，不抄密钥值。官方入口见 [详细设计参考来源](2026-09-30-agent-platform-detailed-design.md)。
- 明确试验／开发能力与生产能力区别，许可有效期、生产使用权、停服／续期条件、付费项、基础设施费用及遥测数据类型／接收端。未知项写“未核实”，不承诺免费。
- 区分必要 license beacon 与可选 tracing／telemetry；不得声称“不配 LangSmith 就完全不出网”。无法满足必要出网要求时报告生产阻断，不私自绕过许可或换成自研 Runtime。
- 现有 Compose 只作为仓库现状；没有官方生产支持、容量、备份恢复、安全和许可证据，不作为生产已可用方案。
- 新增费用、外发目标、遥测数据、云服务和正式部署逐项提请批准；冻结业务设计不自动授权购买、生产迁移或传输企业原件。当前不发起这些动作。

### 4.4 A0-04 异步协作验证契约

1. 同一部署登记主图和受限子图，使用所选版本原生 Agent Protocol 接口。不同模型不等于第二套 Harness，子图不能绕过网关、权限或根级保护。
2. 记录 native thread 与每个新 native run，保持稳定 root 身份。追加指令触发同 thread 新 run 时，核验原生并发／中断策略、要求版本和旧结果资格，不假设“原 run 原地修改”。
3. 优先使用原生子完成通知／事件恢复。若需要补偿，只在同 Runtime 边界用非 LLM reconcile 核对既有运行事实、去重后触发原生继续，不建立另一套 executor、通用队列或长期轮询主 Agent。
4. 以 root、child native run、完成事件及已消费状态形成可持久核对的去重依据；重复通知、乱序、通知前后崩溃、已取消后迟到必须不重复整合／派生／计量。
5. 提供两个实际获准不同模型子任务执行时间重叠的证据；等待期间主完成一项独立工作。模拟阶段证明机制，获准真实模型阶段另证模型和并行事实。
6. 没有可验证的原生通知或同 Runtime 补偿恢复路径，A0-04 不通过；不能退化为单 Agent 聊天或让主靠成功轮询无限“等待”。
7. 原生 async `launch/check/update/cancel/list` 全部经当前 root 子映射和服务端身份校验；拒绝模型猜 task／thread／native run ID 读取或取消其他员工及不属于当前 root 的子运行。原生服务身份不能绕过该映射。

### 4.6 AG-16 累计终止验证范围

- 为每项实际终止机制登记配置来源、有限值、计量对象、原生覆盖范围和触发行为；本计划不指定未知次数／时长，不借用 WorkBuddy 内部数值。
- 持久 root 累计必须覆盖主／子模型调用、工具成功查询、重复子派生、自动创建领域任务及领域模型调用；不能仅沿用单 DocumentTask 上限、单 run 图步数或网关限频。
- 对并行准入采用现有事务／锁／fence 或 Runtime 可验证的原子能力；分支不各自领取完整根额度，保留在途准入与最终记录，失败重试也累计。技术额度不是金额预算。
- 普通问答有 conversation 技术 root，转为实际工作只新增 work／requirement 关联，不清空既有计数；空 work／requirement 能问答而不能创建／修改领域记录。
- 重启、resume、restart、重新领取、更新新 native run、子派生及自动领域新 task 均保留已经消耗的累计及原定截止约束。root 标识由服务端绑定，不接受模型另造 root 逃逸。
- 模拟持续成功却无有效进展的查询、持续派工和持续新建领域任务，证明有限终止；实际进展查产物／业务状态，不信“正在推进”。
- 到达终止条件后禁止新调用和派工，向子及领域提交 guard 传递失效；处理在途返回，不继续自动恢复，不假报完成。技术终止后仅用户明确发起新的工作 root，保存 predecessor 与旧消耗历史；不得自动 retry、重新领取或清空旧累计。普通可重试失败也只能在原 root 剩余保护范围内继续。
- 终止后的非 LLM 取消、状态核对及审计收尾走受限维护路径，不被业务动作门禁封死。测试终止后能完成子／领域停止与迟到对账，且维护路径无法重新启动模型、派工、业务写或发布。
- 加入正常有限工作的通过用例，防止保护把正常工具读取全部禁用；对不存在可证明全范围有限机制的实现判不通过。

### 8.3 财务发布的最小反例集

1. 同部门 A、B 各有草稿；A 只确认自己的精确修订：新 pub 不含 B 未确认内容，B 旧 pub 行仍保留。
2. A 发布后修改本人草稿：看板保持原 pub，不能用最新 workbook 覆盖；同部门 B 修改 A 的记录被拒绝；pub 修订有实际 actor、时间、source hash 和基线。
3. 业务 owner 文本恰好等于登录名、被修改成另一员工名、导入携带 draft_actor 或伪造 record_id：不改变真实填写权／发布权。
4. 精确修订与当前草稿不同：显式展示差异并验证可发布性，不能静默替换为最新草稿；发布基线已变则冲突退出。
5. 删除草稿行不隐式删除 pub 行；发布删除必须是本人获准的明确变更，不可顺带删除他人已发布记录。
6. 旧整部门 submit／publish 仅作兼容桥接；新财务自发布不能经过旧路径把当前整簿所有草稿一起发布，兼容入口也须防旁路。
7. 旧记录 writer 无证据：维持现已发布快照可追溯，不按部门、最后修改人或字符串批量归属；认领／核实按明确授权与证据办理。
8. 已获准财务填写账号只能发布本人精确修订；旧 can_publish 不宽授员工，department grant 或旧整簿发布端点不能成为带入他人草稿的旁路；工程／售前写权限不因财务自发布扩张。

9. B 通过直接请求、整簿保存／导入、删除／替换、改 record_id 或伪造 record_author_id／draft_actor_id 修改 A 的记录均被拒绝，整次请求不提交，A 的原记录及 pub 不变；A 编辑本人记录的正常路径在原授权范围通过，整簿中未变的 B 记录原样保留，不误拒绝本人编辑。

以上用例全部**未执行**，采用已确认的 Q-FIN-01 禁止跨员工编辑规则；业务答复不代表这些权限用例已通过，也不等于整稿批准。

### 8.4 GM 与用量验收要点

- 员工工作列表可以含进行中／失败／取消，经营看板仅读 pub，调用分析不等于绩效。GM 可看批准业务原件，不可因摘要链接进入员工 private conversation／memory 或 native thread。
- “打开第二个”仅使用服务端先前授权集合；对象失效、撤权、删除或集合歧义时重新校验／澄清，不按模型任意 ID／URL 打开。
- 私人附件未登记为业务来源时仍隔离；GM 对源文件的读取／下载也经过原业务授权与删除标记。已合法导出文件不能虚称远程收回。
- 模型重试按实际 physical call 单独累计，重复通知／统计连接不再计一遍；缺失 Token 保留 unknown，不能用零、估值或配置 Token 上限替代实际值。
- 事后费用只有可追溯真实 usage 和价格版本才展示；本轮不建立费用预算系统，无新增支付或模型外发授权。

### 9.3 HR 切换与迁移的必要步骤

1. 在批准隔离库演练备份与分类；记录明确切换边界、授权状态、原截止事实、删除标记、现存原件及派生引用。不以文件仍存在推导对象有效。

3. 新对象及经分类纳入的仍有效存量长期授权归档；旧已失效集合仍拒绝访问，不能简单删除所有 cutoff 过滤而复活。任何旧失效恢复须另获明确对象范围授权，当前不做；已删除不恢复。
4. `run_hr_worker.py` 的周期清理、`cleanup_hr_history.py` 兼容入口及部署调度不得继续对长期归档做年龄删除；保留经过授权的人工删除、真实无引用文件及删除标记重试，不能借“孤儿”按年龄清掉仍引用原件。
5. 撤权／删除后拒绝源读取、下载和新调用；索引、缓存、管理结果集合与历史摘要不能泄露原文；恢复前已加载 checkpoint／外置上下文来源重验。必要删除审计保留最小事实，不拿聊天副本保存可访问简历。
6. 备份与原件同样敏感；备份恢复不复活删除标记或把旧失效对象放回有效集合。备份保留／销毁按获准规则，长期业务归档不等于所有备份永久且无限可读。
