## 2. 一套底座与复用关系

### 2.1 运行链路

员工工作台 → 现有 Django 身份与授权 → 平台 Agent 入口 → Deep Agents Harness／LangGraph Runtime → 获准模型网关与领域工具 → 现有业务服务／Worker／对象存储。

主／子 Agent 在同一运行服务中使用独立 thread 与原生 run；平台保留业务关联、权限上下文、根运行保护和公开事件。Runtime 负责模型循环、异步任务和恢复，原业务 Worker 负责领域任务租约、fence、版本与产物。两者不可互相冒充，也不另外建设第二个通用调度框架。

| 现有落点 | 沿用能力 | 最小接缝 |
| --- | --- | --- |
| backend/portal/models.py、security.py、operations.py | 账号、角色、模块授权、会话版本 | 单部门归属、运行身份快照、受限员工管理，不放开完整运维权限 |
| backend/portal/model_gateway.py、model_api.py、model_messages.py；model_gateway/app.py | 模型权限、服务身份、网络、调用日志 | 单独 Agent 工具协议及适配器，旧纯文本接口不放宽 |
| product_models.py、product_service.py、product_api.py、product_worker.py | 文档任务、蓝图、版本、幂等、租约与取消 | 领域引用、根运行关联、要求变更与终止的提交校验 |
| product_source_api.py、product_source_service.py、product_storage.py | 来源授权、文件存储 | 只暴露有边界的检索／读取／资料引用，不暴露宿主文件系统 |
| product_workflow.py、product_outputs.py、product_history.py、product_workspace.py | 固定领域图、产物下载与历史 | 原图继续处理原领域任务，不将其当作自主主／子 Agent Runtime |
| hr_screening_models.py、hr_screening_api.py、hr_screening_results.py、hr_screening_worker.py | JD、批次、简历与筛选任务 | 薄工具接入、授权资料归档与根运行关联 |
| hr_resume_storage.py、hr_retention.py | 文件授权、清理与删除标记 | 统一取消新策略的自动到期，不只更改列表显示 |
| business_models.py、business_boards.py | 部门工作簿、记录、不可变修订、经营看板 | 记录身份、本人精确版本发布、已发布快照合并；不重建账本 |
| work_summary.py、现有 ModelCallLog | 工作摘要、真实模型消耗 | 类型化对象引用、调用关联和未知消耗展示，不再建一套 Token 账 |
| frontend/src/centers/CenterWorkspace.tsx、BusinessLedgerWorkspace.tsx | 门户、工作台、部门台账 | 替换 assistant 重定向分支；财务入口复用 onlyDepartment 限定视图 |

backend/portal/ 表内省略前缀的文件均位于该目录；拟新增文件最终以实施计划为准。现有业务服务的权限、金额计算及领域校验不是 Agent 可以绕过的内部接口。

### 2.2 SDK 与部署选择

设计选择 Deep Agents Harness；元数据核对的候选为 deepagents 0.7.19，**不是兼容性结论，也不声明为最终锁定版本**。A0 使用隔离环境验证 Python、LangChain／LangGraph、模型适配器和持久化依赖后再锁定版本与依赖文件。

异步委派优先使用 AsyncSubAgent 与 Agent Protocol 的同部署运行图，launch／check／update／cancel／list 沿用原生生命周期。官方 standalone 路线涉及 PostgreSQL、Redis、许可／服务身份和潜在许可验证出网；不得凭 SDK 开源许可证推导 Runtime 免费或可任意生产部署。Docker／Compose 示例不能直接当作生产验收。

A0 必须列出运行服务的许可、必要服务、硬件、获准出网与遥测配置。新增付费或明显改变成本、业务内容外发或替换 Harness 先询问用户；不自行编写完整 Agent Protocol 服务来绕过许可。默认禁止向外部追踪系统发送提示词、附件、工具原文和个人信息。未找到满足批准边界的运行路线时阻塞依赖批次，不隐瞒为开发细节。

## 3. 身份、数据与所有权

### 3.1 最小逻辑记录

以下是必须表达的逻辑事实，不要求每行建一张新表；已有记录能安全承载就复用，不复制领域正文、结果、账本或 Runtime 全部检查点。

| 记录 | 最小字段／约束 | 保存位置与职责 |
| --- | --- | --- |
| User.department_code | product／hr／finance／engineering；普通员工恰属一个部门 | 扩展现有 User，与多角色授权分开；旧账号无法确定时标为待分配，不猜测 |
| AgentProject | UUID、owner_id、department_code、name、timestamps | 名称唯一必填；不与财务 project_id 或 DocumentTask ID 混同，不提供跨员工协作 |
| AgentConversation／Message | owner、department、optional project／work、message_id、role、content／attachment references、timestamp | 私人会话；普通问答可没有业务工作；不保存私有推理或凭据 |
| AgentWorkTask | owner、department、optional project、goal、current_requirement、state、result references、timestamps | 一次实际工作归档；失败取消也保留，不按每条聊天建工作 |
| AgentRequirement | work_id、version、user_message_id、source versions／hash、received／applied 标记 | 不可变要求版本；唯一 work_id + version；精确区分接收与生效 |
| AgentRun | run_id、stable root_run_id、parent_id、conversation_id、optional work_id／requirement_version、runtime thread／current native run ID、state、deadline、policy snapshot | 主／子运行映射；恢复和原生 update 的新 run 不能创建新 root 或重置消耗；普通问答也有技术 root，但不强建业务工作 |
| AgentEvent | owner／work／run、seq、event_key、type、public payload、timestamp | seq 递增、event_key 幂等；仅公开状态与摘要，不另做事件溯源引擎 |
| AgentBusinessReference | work／root／requirement、domain type、object ID、revision／hash、operation key | 指向现有业务记录；唯一领域操作键；不复制完整简历和正式文档 |
| AgentSkillInstallation | owner、catalog skill ID、enabled、immutable version／digest | 本人安装状态；共享审核目录只读，运行保存实际使用版本 |
| Attachment reference | owner、storage key、type／size／digest、source scope、deleted marker | 复用私有存储及文件校验；私人附件不因上传而自动成为 GM 可读业务原件 |
| ModelCallLog 扩展关联 | root／run／conversation、optional work／requirement、physical_call_id、model、actual usage／unknown、timestamps | 每个实际请求唯一记录；真实重试是另一次实际调用，不按事件或展示重复计费 |

业务来源用对象版本或内容摘要固定；运行使用权来自服务端身份和最新授权，不来自模型自己填的 owner、department 或 root ID。每次读取／写入同时核对所属对象与授权版本。

账号部门、台账类型和旧页面 Center ID 分开映射：既有 presales 台账不新增第五个员工部门，产品员工仅在已有／获准台账授权范围使用；工程页面的 cost 标识与 GM 的 business 标识保留为路由兼容，不拿页面标识推定员工组织归属。

### 3.2 权限矩阵

| 主体 | 可读 | 可写 | 不可获得 |
| --- | --- | --- | --- |
| 员工／本人主子 Agent | 本人会话、工作、项目、个人安装状态；已获业务授权对象 | 本人运行范围和部门允许的草稿操作 | 其他员工会话／记忆／运行文件；未授权业务资料；审核、发布、账号管理能力 |
| 总经理本人及只读助手 | 获准跨部门工作摘要、状态、成果、业务原件、已发布经营数据与用量汇总 | 助手本人私人会话；人操作受限员工账号管理入口 | 员工完整对话／个人记忆／运行后端；业务编辑、代发布、删除；平台管理员提权 |
| 平台管理员 | 现有运维权限范围 | 现有账户与配置运维 | 不凭管理员身份自动取得业务资料或完整员工对话 |
| Runtime 服务身份 | 当前有效 root 授权的工具与后端作用域 | 当前要求版本与 fence 允许的动作 | 宿主任意目录、任意网络、模型凭据选择、替代员工审批 |

总经理的业务只读和员工管理是两种不同授权：后者只允许经现有校验的普通员工创建、单部门分配、允许角色／模块调整和停用；不得授予管理员／GM 角色、取得凭据或修改他人运维配置。不得给 GM 放开完整 operations.py API，账号操作也不暴露给 Agent 工具。

所有者确认蓝图、本人发布、人工删除及正式对外发送保留人操作边界。模型输出“已批准”无效；内部领域服务仍执行与人 API 相同的校验。撤权后，检索缓存、历史摘要和下载链接不能作为绕过途径。

## 4. Agent 配置、工具与后端

### 4.1 主／子 Agent 的实际职责

主 Agent 根据部门与已授权工具处理澄清、资料核对、分解、委派、更正和结果整合。简单任务直接执行；需要事实而工具没有结果时请求补充，不用模型常识伪装企业事实。主 Agent 可动态选择审核过的子 Agent 能力／模型预设，而不是要求用户手选模型或先搭固定团队。

子 Agent 首期仅一层：拥有独立 thread、明确目标、最小资料引用、允许工具列表与获准模型绑定；不能再派子 Agent。至少两个模型预设须在 A0 验证真实服务可用和工具能力，模型名不同、配置对象不同不等于实际模型不同。子 Agent 无权修改根权限、终止配置或技能审核目录。

上传文件、检索片段、网页与工具原文只作为证据数据；其中要求切换身份、读取其他账号、安装技能、跳过确认或外发资料的指令不获得执行权。服务端权限不依赖模型正确识别注入，负向测试须覆盖模型已经提出越权工具调用的情况。

| 配置层 | 内容 | 控制方 |
| --- | --- | --- |
| 平台硬边界 | 身份、部门、允许模型、工具上限、运行根与终止策略 | 服务端生成；不可被提示词、技能或用户消息覆盖 |
| 部门说明 | 目标、真实数据来源、可用业务工具、人工确认边界、输出标准 | 审核后随代码／版本发布，员工不能升级权限 |
| 技能 | 少量内置资料整理、文档质量检查、招聘筛选说明 | 审核目录按版本只读；仅声明必要获准工具，安装不扩权 |
| 工作上下文 | 当前目标、要求版本、获准来源引用、已完成成果摘要 | 主 Agent 可组织；身份及来源授权由服务端重验 |
| 委派消息 | 一项清晰子目标、允许输入／输出、能力预设 | 主 Agent 选择；服务端校验并注入 root／owner，不信任模型 ID |

无需手动安装技能也能完成部门基本工作。卸载影响后续启动，不暗中改变在途运行绑定的版本；若版本因安全问题撤回则阻断新动作并记录原因。首期不提供员工上传可执行技能、任意 pip／npm 安装或网络下载插件。

### 4.2 工具面与数据面一起隔离

业务工具只包装现有领域服务：获准检索／读取、资料引用、建立或更新草稿任务、查询状态、生成已获确认的产物、获取授权结果引用。模型不能直接用审核／发布／删除／部署／用户管理端点。领域写操作必须带服务端幂等键、对象预期版本、当前要求与 root fence。

Harness 默认工具也属于攻击面。A0 逐项导出主／子 Agent 的实际注册清单，包含文件读写、目录枚举、搜索、上下文外置、自动加入的委派和内部后端操作，逐项标为允许／禁用／需要包装。不能只检查手工定义的业务工具。

原生异步 launch／check／update／cancel／list 同样须绑定平台保存的本 root 子运行映射：模型传入的 task／thread ID 必须属于当前授权 root，list 只返回该范围，不能用共享 Runtime 服务密钥读取或取消另一个员工的原生 thread。所选版本缺少该校验时仅在原生工具／服务授权入口补薄包装，不重写生命周期引擎。

| 后端区域 | 作用域与行为 | 不允许 |
| --- | --- | --- |
| 临时工作区／上下文外置 | 虚拟 owner／root／run 命名空间；路径解析、读取和内部写入均校验；并行分支独立写区 | 宿主根目录、路径穿越、符号链接越界、猜测他人路径 |
| 同一工作的共享结果 | 显式授权的只读结果引用，由主 Agent 整合；不是共享可写目录 | 子 Agent 任意改同伴文件、别人的运行记录 |
| Store／长期状态 | 按 owner 与受授权 work 命名空间；恢复仍校验当前权限；首期不启用自动共享学习 | 全局无过滤搜索、GM 直读私人记忆、撤权后依赖旧授权继续读 |
| 检查点与 Runtime thread | 服务身份可访问当前授权运行；入口与内部 API 均受保护；不直接对浏览器暴露原生服务 | 可猜 ID 的跨账号 restore、读取全部 messages、写入他人 checkpoint |
| 共享 Skills 目录 | 审核版本只读；安装只是本人引用与启用记录 | 员工或子 Agent 写目录、覆盖共享提示、间接加载任意代码 |
| 原业务对象存储 | 复用授权读取／下载／删除标记；引用有类型与版本 | 将私人文件复制到通用公开下载路径 |

不使用暴露整个宿主目录的 FilesystemBackend，也不开放无沙箱的 LocalShell。无需为了“Agent 会执行”增加终端能力。内部文件转存与上下文压缩也经过身份作用域，不能只在工具参数上做前端过滤。

## 5. 页面与接口契约

### 5.1 保留原入口、追加助手

产品／人事／财务部门工作台保留现有列表、详情、上传和下载页面。CenterWorkspace 的 assistant 分支由重定向改为助手页面，不重写公司壳、侧栏、深链、权限刷新和键盘可访问性。工程仅保留原业务与接口接入，工程助手由另一负责人交付，不假造已可用入口。

助手初始页面提供一个输入框、附件、少量技能入口、“创建项目”按钮和本人历史。项目只填名称，服务端确定 owner／department／UUID；可不选项目开始工作。财务单独入口复用 BusinessLedgerWorkspace 的本部门限定模式，不复刻 GM 全部门经营页。

输入区分普通问答、查询进度、当前工作更正、新目标；只在歧义会改变对象或产生副作用时询问。进度查询不重启任务；普通问答不强制创建工作或项目。进入实际执行前持久保存 work 与当前 requirement，展示用户可见摘要；不按聊天条数统计成果。

工作页展示要求、接收／生效时间、真实状态、子任务简要详情、来源、版本、成果预览／下载以及取消／明确重试。保留连续输入；更正不会被“任务正忙”静默丢弃。不会显示私有推理、模型密钥或 Runtime 原生完整状态。

| 用户动作 | 可见反馈 | 服务端事实 |
| --- | --- | --- |
| 提交消息 | 已接收，返回 message ID | 重复客户端请求不重复写入；消息接收不冒充执行成功 |
| 更正要求 | 版本 N 已接收；稍后生效／待澄清 | 生效须完成领域版本／fence 协调并由 Runtime 接入；不能仅 UI 改标签 |
| 产品确认蓝图 | 展示精确版本／输入摘要，所有者本人确认 | 沿用人操作入口，校验 input／grant／rules hash；Agent 无批准工具 |
| 关闭／重开页面 | 后台继续；按授权补读 | 重开不产生新运行；网络断开不标任务失败 |
| 取消 | 先显示停止处理中，再显示终止原因和已有成果 | 新调用立即禁止，领域任务和子运行的停止结果可核对 |
| 财务发布 | 选定本人记录与精确版本，显示发布差异 | 不把同部门其他人的未确认草稿带入快照 |

### 5.2 平台公开 API（拟新增）

采用现有 /api/ 的认证、CSRF、错误结构和对象授权习惯。下表是最小契约，不是允许暴露 Runtime 原生 API；具体 Django 路由及类型生成在实施阶段完成。

| 路由／方法 | 输入重点 | 输出／安全约束 |
| --- | --- | --- |
| /api/agent/conversations/ GET／POST | 可选 project_id，创建请求键 | 本人会话列表／ID，不返回员工间对话 |
| /api/agent/conversations/{id}/messages/ GET／POST | text、attachment refs、client_request_id、可选目标 work | 授权分页／message ID／绑定工作；重复请求返回同一事实 |
| /api/agent/projects/ GET／POST | name；其他身份字段拒绝或忽略 | 本人项目；不因同名合并，不按模型推定所属 |
| /api/agent/work/ GET；/{id}/ GET | 分页、状态、可选本人项目 | 本人工作摘要、要求版本、类型化成果引用 |
| /api/agent/work/{id}/requirements/ POST | expected_version、message_id、明确更正内容 | 新不可变版本；冲突返回当前版本，不静默覆盖 |
| /api/agent/work/{id}/cancel/ POST | expected_version、request_id | 幂等终止请求，领域停止与在途状态可追溯 |
| /api/agent/work/{id}/retry/ POST | 当前失败／终止版本、request_id | 显式请求；技术额度耗尽时需明确发起新的工作关联，不自动 reset 旧 root |
| /api/agent/work/{id}/events/ GET | after_seq、分页／流式模式 | 有序公开事件；重复可去重，断线可补读，无权则拒绝 |
| /api/agent/skills/ GET；/installations/ GET／POST／DELETE | 审核 catalog ID、版本、enabled | 本人启用状态；不接 URL／可执行代码／工具权限声明 |
| /api/agent/management/work/ GET；/usage/ GET | 获准部门／员工／时间范围 | GM 摘要或实际消耗，独立于私人会话和运行后端 |

GM 原件通过类型化对象引用转到既有业务读取入口，入口补充批准的只读授权并重验对象；不接模型给出的任意 URL。受限员工管理使用独立人操作端点，复用现有账号校验，不嵌入只读查询工具。不得为了 GM 原文访问开放完整原员工工作台写权限。

分页游标和事件 seq 绑定所属对象；跨账号错误不泄露原文、目录、凭据。浏览器只能访问平台投影，Runtime 控制入口置于受服务身份保护的内部网络。

### 5.3 模型与内部工具协议

保留现有文本 Message 的 system／user／assistant 及原校验，新建隔离 Agent 协议：支持 tool 角色、assistant tool_calls、tool_call_id、结构化工具参数与工具结果；允许仅 tool_calls 的 assistant content 为空。工具 schema、名称、类型和长度／深度必须校验，缺失或孤立的调用 ID 拒绝；不会通过放宽旧接口接受任意消息。

适配器必须验证模型真实支持工具调用、流式／非流式结果、多个 tool_calls、工具错误、未知 usage 和实际重试；原生接口能力不同通过隔离适配处理，不伪造模型返回。模型、base URL 与密钥由现有授权网关决定，模型输出不能选择凭据或绕过网络白名单。

内部执行上下文由平台签发或以受保护映射加载：actor_id、department、work_id、root_run_id、run_id、requirement_version、grant／session_version、fence、allowed models／tools、deadline。Runtime 服务身份不是万能账号；每次模型准入、读取和副作用重新核对 root 状态、当前权限与对象版本。浏览器或模型提供同名字段不构成授权。

普通问答的执行上下文绑定 conversation 与技术 root，work／requirement 可为空，但仍受身份隔离与累计保护；确定性业务写工具在关联有效 work／requirement 前一律不可执行。问答转入工作时保持同一 root 消耗并建立业务关联，不能先运行无额度的“分类／聊天”循环再重新计数。

业务工具结果统一表达 operation_key、domain type／ID／revision、status、source references、public summary 和错误；原始资料按需限量读取，不把完整库返回给模型。写入成功后响应丢失时按操作键查领域事实，不盲目重做。

## 6. 执行、更正、取消与恢复

### 6.1 业务状态与 Runtime 状态分开

工作状态投影限定为 queued、running、waiting_input、waiting_confirmation、stopping、completed、failed、cancelled、terminated。这不是重新实现 Runtime 全部状态机；每次变更必须有公开原因及原生／领域事实。技术上限终止与用户取消、业务失败分开记录。

| 转换 | 条件 | 禁止 |
| --- | --- | --- |
| queued → running | 当前权限有效、根运行准入、Runtime 已核实接收 | 发请求即假报成功启动 |
| running → waiting_input | 缺失决定执行路线的资料或要求 | 编造事实补齐、无限“查询进度”当进展 |
| running → waiting_confirmation | 产品蓝图已形成，需要所有者精确版本确认 | 模型代确认、为普通问答增加审批 |
| waiting → running | 新资料／确认匹配当前要求和版本，恢复准入通过 | 用旧 blueprint hash 接受新要求 |
| running → completed | 当前有效要求的成果已提交，必要子／领域任务结束，本次 Agent 交付范围内质量条件满足，不含正式使用前人工签收 | 原生主 run 结束但后台未完成即工作完成；将未签收作为交付完成门禁 |
| 任意非终态 → stopping → 终态 | 取消、撤权或累计保护；停止新动作并处理在途任务 | 仅让页面显示停止，而领域 Worker 继续发布当前成果 |
| failed → 明确重试 | 用户请求匹配版本，权限和根保护重新核对 | 无限自动重试，未知外部结果直接再写一次 |

需要等待用户时不保留模型连接、业务锁或并发槽。活动执行时间、总截止时间及等待规则由 A0 在有限配置中验证并记录；等待／恢复不得清零已消耗额度或无意延长原定截止条件。明确用户继续动作也不能把旧 root 的消耗抹掉。

### 6.2 可靠启动与异步委派

1. 人消息、工作、要求和逻辑 root 在平台事务中先持久保存；启动意图挂在现有最小运行记录上，以稳定 operation_key 标识。不另引入一套消息总线作为前提。
2. 唯一受保护的运行适配入口领取启动意图，在原生 Runtime 创建／查询 thread 与 run。发送结果未知时，先按稳定标识查原生事实；所选接口不能安全查重时 A0 阻塞，不盲目重复创建。
3. 主 Agent 通过原生 launch 提交独立子目标，服务端注入 root、当前要求和最小权限。launch 返回后主 Agent 可以继续自己的独立工作；等待子结果时释放活动资源，不用模型忙轮询。
4. 子完成优先使用原生通知／事件机制。若只有状态读取，使用同运行服务中的最小非 LLM 状态核对，有限间隔、背压、去重，并接入同一 Runtime 的主线程；不再建通用 DAG 引擎。
5. 接纳结果的幂等键为 root + child logical ID + native run ID + requirement_version。核对实际权限、来源版本、是否取消及根额度；旧要求结果只归档，不覆盖当前成果。
6. 通知到达不能无条件唤醒另一个并行主 run；适配器核对主线程状态，在原生允许的串行边界接纳或排队。崩溃后按未接纳记录恢复，不要求模型自觉去重。

AsyncSubAgent 的 update 可能中断旧 native run 并在同一 thread 创建新 native run。平台保留这些原生 ID 与中断原因，logical run／root 及累计保护不变；不能宣称同一个原生执行无缝续跑。主任务的后续接纳也可能是同一 thread 的新原生 run，须如实记录。

### 6.3 连续更正与领域提交

要求更正先持久保存新版本并撤销旧版本的提交资格，公开事件标记 received。根据影响范围更新／取消子运行、推进原业务对象版本或 fence，必要时重新确认产品蓝图；直到运行接入和领域守卫均协调完成才标记 applied。协调失败时保留“待生效／失败”原因，不继续承诺按新要求生成。

复用产品 _guard、租约／fence、输入／授权版本、蓝图确认及 _store／_finish；在其共享提交路径增加必要的 root／requirement 关联校验，不能只在 Agent 回复阶段丢弃过时文本。任意途径调用的领域 Worker 都不能将旧要求产物作为当前版本。旧产物可以保留历史，下载和展示仍按原对象授权。

root 可执行校验针对 Agent 发起及其派生的执行动作；独立人操作和未关联 Agent 的旧任务仍按各自授权、当前领域版本／guard 校验，不以存在活动 root 作为确认、本人发布、查看或下载的通用前置。执行来源由服务端入口和可信运行关联确定，Agent 工具不得省略 root 冒充人操作；人操作若触发后续 Agent 执行，该执行仍须通过根运行准入。

新要求影响来源、目标、金额依据或输出规范时，既有蓝图批准快照失效，任务所有者确认新精确版本后才能重新生成；这不是恢复第二审核人。无关展示调整可沿用批准，但差异分类须有确定性规则与测试，不能由模型自行豁免门禁。

### 6.4 终止与未知结果

取消入口首先事务性标记 root 停止并提升提交 fence，阻止新模型请求、工具副作用、派工和领域领取；随后调用原生取消及原领域取消服务。等待在途任务报告或超时核对后形成终态，保存已完成有效成果与真实失败原因。撤权使用同一保护入口，重新恢复时不能继续采用旧 grant 快照。

停止后的原生取消、领域状态核对和审计收尾由非 LLM 服务生命周期执行，不被“禁止新业务动作”一并封死；仅限终止收尾，不能再发起模型请求、生成新成果或新派工。

已发送模型请求可能不能撤回：记录实际完成／取消状态与可得 usage；迟到结果不得引发新调用或覆盖当前成果。已经提交的外部操作不能假装被回滚，须按操作键核对并向用户说明。用户取消不删除历史，人工删除另外走获准人操作入口。

重启恢复按 root 映射、原生检查点和领域事实逐项核对；输入／结果本身不是检查点。检查点写入失败与领域提交成功之间的故障通过 operation_key 与业务修订查重；没有查重证据不得再次写入。原生状态丢失时显示恢复失败／待核对，不从聊天摘要自动重做一切。

恢复前还要重新验证已装载来源的可访问性；含撤权／已删除原文的检查点、外置上下文和缓存不得直接回放给模型。无法安全剔除受限内容时停止恢复并要求在当前获准来源范围重建上下文，不以“此前已经读过”为理由继续使用。

### 6.5 累计技术终止与真实计量

现有网关限频／并发限制及单个 DocumentTask 的模型调用上限保留，但不能代替整个 root 的有限保护。A0 先证实所选 Runtime 的覆盖范围；只对未覆盖处在现有运行记录和日志上补最小关联／原子准入。

| 检查点 | 必须覆盖 | 持久规则 |
| --- | --- | --- |
| 模型调用准入 | 主／子实际请求、适配器重试、派生领域 Worker 的模型请求 | 相同 root 累计；同 physical_call_id 查重，每次真实重试另计；准入与占用原子化 |
| 工具准入 | 成功查询、自动文件工具、重复无进展操作、业务写入 | 无论成功失败均进入技术次数／截止保护；后台内部读写仍有身份校验 |
| 委派与领域启动 | 重复派工、并行分支、新建领域任务 | 共享根额度；子不能各自复制整份额度；原业务流程的非 Agent 任务仍沿用原保护 |
| 并发与时间 | 在途调用／子任务、活动执行时间、固定截止条件 | 已准入动作按同一 root 领取；恢复和重领不 reset；等待规则有明确配置来源 |
| 无有效进展 | 无限成功 status 查询、重复生成同一目标 | 有限动作／时间先保证终止；有效进展依据业务状态／产物，不信模型口头表态 |

根策略在启动时固定并记录配置来源；不在草案编造次数、秒数或 WorkBuddy 内部参数。未知 usage 不按 0 计，也不阻止记录调用次数；缺失／损坏的保护状态应拒绝继续准入而非默认无限。达到条件时阻断所有新动作，并向原生子运行、领域 Worker 提交守卫传递终止。

技术准入记录与实际消耗分开：进程在占用后、发出前崩溃可以留下待核对动作，不能伪造已发生 Token；外部是否执行未知时也不能立即释放占用导致重复发送。恢复按唯一动作 ID 核对，明确未执行才释放并发占用，累计已发生消耗不回滚；这是技术保护，不是金额预留。

模型费用仅可由真实 usage 与可追溯价格版本作事后展示，不成为金额预算门禁；没有价格依据不输出估算费用。技术终止后如需继续，用户须明确发起新一轮工作，保留 predecessor 与旧消耗；模型、Worker 或后台恢复不可自动创建新 root 规避保护。

## 7. 各部门工作闭环

### 7.1 产品：从资料到正式三件套

流程为澄清目标 → 读取获准上传／知识来源 → 事实表与缺口 → 必要子任务资料分析／独立检查 → 草案／蓝图 → 所有者精确版本确认 → 原领域 Worker 生成 → 检查修正 → Word 技术方案、Word 可研、PPT 归档与下载。

Agent 不重写原文档引擎和存储。RAG／联网补查仅在真实服务已配置且获准时开放；无可用服务显示缺口／请补资料，不用“已搜索”伪造检索。首期不开任意浏览器，不向未知站点外发原文。技术方案与可研引用来源版本，缺投资、规模、价格或收益依据时不能编造。

蓝图确认沿用 [单用户设计](../../docs/superpowers/specs/2026-09-24-product-single-user-generation-design.md) 的任务 owner、版本及输入／规则／授权摘要约束。reviewer 旧字段不恢复授权意义。正式长度按 [现有标准](../../docs/product/FORMAL_LENGTH_20260929.md)：技术方案不少于 50,000、可研不少于 70,000 个非空白正文字符，且须是真实有用内容；小原型往返通过不能替代正式质量验收。

### 7.2 人事：复用筛选，改变保留策略

流程为选定／形成 JD → 上传获准简历或引用当前批次 → 原筛选服务执行 → 查询真实任务状态 → 返回匹配依据、风险、排序及来源 → 人工核对与归档。筛选结论不等于录用决定；不接 BOSS、外部招聘抓取或未经批准的个人资料源。

新策略不自动到期：JD、获准简历文件、筛选请求／批次／结果与工作关联保持授权归档，模型只能读取当前获准对象。实施时同时盘点 hr_retention.py、API 查询、读取／下载、Worker、清理任务、缓存和上下文引用中的旧到期条件，不能只停清理脚本留下读接口继续拒绝，或只延长页面显示而文件被删。

已删除文件／删除标记不恢复；旧规则下已失效但尚未删除对象不自动重新开放。迁移仅保留仍有效对象并记录存量分类；如需恢复旧失效对象，另外取得明确对象范围授权。人工删除和撤权继续生效，相关模型上下文／索引引用作失效处理，不用聊天副本保留可访问简历。保留不等于模型全库读取或外部遥测许可。

### 7.3 财务：草稿与本人发布分开

沿用部门工作簿、JSON 记录、不可变 BusinessLedgerRevision 及既有金额口径。当前 finance.owner 是“回款负责人”文本，不能作为记录填写账号或授权字段；新设计为记录建立稳定 record_id、不可由员工变更的 record_author_id 和各修订 draft_actor_id。record_author_id 由服务端在可信创建时绑定实际填写账号，各次财务修订的 draft_actor_id 必须为该账号；旧数据无法核实填写人时待认领／核实，不以字符串或整簿最后操作人猜身份。

用户自然语言只能在本人允许范围整理／填写草稿并预览差异；不自动发布。人操作发布须绑定本人 actor、选定 record_id、每条精确 source revision／hash 和预期已发布基线，事务内重验权限及版本。现有整部门 submitted／published 流程只作兼容桥接，不能把“整个工作簿当前更新人”当作每条记录填写人。

已有获准财务填写账号的发布能力按本次确认映射为“仅本人精确修订自发布”，不再等待第二审核人／整部门发布者；不得直接给所有员工授予现有整部门 can_publish 的宽权限。未获财务填写授权的账号不因这条规则取得写权，其他部门发布许可不顺带扩大。

新已发布快照 = 上一已发布快照 + 本次获准本人精确修订的增量，不等于当前部门草稿全集。选中新增／修改的行进入新快照，其他人未确认草稿保持不变；发布旧于当前草稿的版本需明确展示差异且检查可发布性，不能静默发布最新行。删除已有已发布行属于显式发布变更，不因草稿删除自动影响看板。

GM 看板及 finance／engineering／presales 数据读取均核对已发布来源；当前 presales 最新工作簿读取须适配为已发布，不把草稿当经营事实。未发布状态或无发布记录应展示缺失，而非退回草稿。工程字段／算法和其他部门写流程不因本轮财务自发布而擅自扩权。

**Q-FIN-01 已确认并关闭（2026-09-30，用户回答“不能”）。** 财务员工只能在原业务授权范围修改本人填写的记录，同部门身份不授予修改他人记录的权限。服务端按 record_author_id 核对每条记录；整簿保存、批量导入、删除、替换记录或篡改 record_id／填写账号均不能覆盖他人记录，拒绝越权请求且保留原记录。Agent 使用本人同样的授权，不因工具或后台执行取得额外编辑权。

整簿保存先与服务端当前记录计算变动，只对新增、修改、删除的记录执行写授权与预期版本校验；未变动的他人记录原样保留。不得因前端提交整簿而拒绝正常的本人单条修改，也不得用重建整簿或换 ID 绕过他人记录保护；越权或版本冲突则整次写请求不提交。

填写人本人确认发布本人精确版本的规则不变，部门级发布不得携带他人未确认草稿；本次答复不改变同事资料的既有读取权限，不新增总经理、管理员代编辑或自动转交记录的权限。存量填写人无法核实时保留有效已发布快照和核实入口，不默认把记录分配给当前操作者。业务边界及整稿已获批准；具体实现和权限用例仍待实际证据。

### 7.4 总经理：查询管理，不接管员工 Agent

三个入口分开：员工工作记录含进行中／失败／取消和成果；经营看板只含已发布数据；使用分析含真实调用、模型与消耗。统计工作或已交付成果须按稳定 work／domain ID 去重，聊天、附件、子任务、重试和多版本不能都当新成果计数。

GM 以自己的身份查询已获准跨部门工作摘要、版本、结果及必要业务原件，包括批准范围内的简历、财务明细和供应商价格；不得进入员工完整聊天、个人记忆、临时工作目录或检查点。私人附件只有经明确业务操作登记为领域输入后才成为可授权业务原件，不因通用上传自动可读。

“打开第二个”只解析同一会话先前服务端返回的已授权结果集合，重新校验版本和权限；集合已过期、歧义或对象失效时澄清，不由模型制造任意对象 ID／链接。撤权／人工删除后旧集合与摘要须失效或过滤；已合法导出的文件无法承诺远程收回，下载审计如实保留。

用量汇总复用 ModelCallLog：实际主／子／领域调用按 physical_call_id 去重；已知 Token 单独求和，未知调用数量明确显示；实际请求重试不被去重为零消耗。展示执行时长、等待时长、完成量的口径，不冒充员工在线时长或自动绩效评定。

### 7.5 工程边界

平台保留既有 backend/portal/engineering_api.py、engineering_models.py、engineering_worker.py 与已发布工程台账入口。对方交付接口后，仅接获准认证、对象版本、请求幂等、状态、结果引用及错误；未交付则标不可用，不模拟工程计算成功。新增工程助手、算法、行业判断及审批流程不在本次平台实现范围。

## 9. 迁移、回滚与上线边界

### 9.1 存量迁移原则

先用隔离数据库验证新增字段／记录、数据映射与备份恢复。普通员工单部门按明确授权来源核实，冲突账号待人工分配；管理身份不强行归员工部门，也不获得业务写权。新项目不批量改写既有文档或台账项目 ID。

领域历史通过引用迁入视图，不复制完整文件和新版本系统。财务记录身份按可核实修订证据补齐，无法核实时不可自动归属、发布或批量清洗。人事存量按有效／已失效／已删除分类，旧失效恢复需另行明确授权，不执行“全部延长保留”的隐含恢复。

备份仍是敏感资料，访问／出网与保留规则受相同授权。人工删除按原业务机制执行文件、索引、派生引用失效；运行文件与检查点残留纳入删除／可访问性验证。对不能即时物理清除的备份如实登记恢复限制，不让旧备份还原为可访问对象。首期自动学习不启用，不能将“长期记忆策略以后定”作为写入无限私人缓存的许可。

### 9.2 回滚与运行维护

新助手可独立关闭入口／停止新运行，旧文本接口、业务页面和原 Worker 保持可用。关闭入口不删除 Agent 历史、不取消用户未要求取消的原独立业务任务；已启动的 Agent root 按唯一运行服务明确停止或收尾，不能遗留无主领域提交。回滚代码不得通过删除表或新记录来伪造无变化。

生产依赖／迁移／发布另行授权；先备份与隔离验证，列出运行服务、网关、数据库、对象存储、监控和回滚检查点。不得在有长任务时默认在线重建／重启旧 Worker，需维护窗口或经证实的平滑切换。Runtime 与原领域任务均须监测无效 lease、挂起 root、事件投递失败、消耗未知和异常出网；无需为本次重新建设通用监控平台。
